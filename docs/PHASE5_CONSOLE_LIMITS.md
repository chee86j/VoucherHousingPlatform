# Phase 5 broker console — scope and limits

- The Next.js console is server-rendered and requires a current, MFA-verified API session. Tokens live in HttpOnly SameSite=Strict cookies, not localStorage or browser JavaScript. A narrow same-origin proxy forwards them only to explicitly listed mutation routes; sensitive reads are server-rendered with a minimal browser payload. Successful browser sign-in requires a working Nest API and database; no real-user login was exercised here.
- The dashboard shows operational-only fields from the first 50 clients/units and first 100 cases/showings/tasks. No voucher program name, household details, notes, documents, or landlord export are intentionally serialized. Pagination, server-side filtered shortlists, and protected data minimization at the Nest API remain follow-ups.
- Case drag is limited to two early, documented FSM transitions; adjacent button actions provide keyboard/touch alternatives. The backend can still reject a move when evidence is missing. Later transitions and document readiness remain blocked. The Phase 2 client `pipelineStage` update endpoint is separate from the case FSM and must be reviewed before anyone treats both boards as authoritative.
- Showing creation records only an internal invitation, not a delivered message. Fit/readiness is not automatically checked on invitation; brokers must verify it manually. No automated selection, numeric applicant score, or landlord disclosure. Attendance and follow-up task completion use backend guards.
- This is **not ready for real client data or deployment**: PostgreSQL migrations and cross-tenant integration tests are outstanding, hash-chained audit is not guaranteed atomic, PII storage is not encrypted as claimed in old schema comments, dependency audit still reports a high `braces` advisory, and token revocation/session lifecycle is incomplete. The cookie expires after 15 minutes (or earlier if the API JWT expires). Ensure HTTPS, correct proxy-origin behavior, and secure MFA-enrollment handling before pilot.
